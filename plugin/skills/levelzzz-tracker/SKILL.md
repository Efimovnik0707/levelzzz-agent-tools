# Levelzzz Tracker

Использовать MCP `levelzzz`: `list_tasks`, `complete_task`, `add_task`,
`delete_task`, `update_task`, `get_progress`, `get_profile`, `get_guild`,
`get_history` и, когда он доступен, `add_proof`.

## Действия

- Перед изменением получить свежие задачи через `list_tasks`.
- В обычном диалоге отмечать выполнение только после явного сообщения
  пользователя и при одном однозначном незакрытом кандидате. При нуле или
  нескольких совпадениях не гадать, а запросить уточнение.
- Автоматический сценарий может выполнять только те мутации, которые
  пользователь заранее явно разрешил вместе с источником доказательств,
  пределами и условиями остановки. Всё остальное оставить read-only.
- `add_task`, `update_task` и `delete_task` вызывать по прямой просьбе либо в
  пределах такого явно разрешённого сценария. Не создавать дубликаты и не
  повторять уже выполненную операцию.
- При 429 не запускать собственный цикл повторов: MCP соблюдает `Retry-After`
  и повторяет запрос один раз.

## Пруф

Пруф — конкретное подтверждение реально выполненной работы. Он считается
валидным от 20 непробельных символов, даёт +25% к урону боссу, но не к XP.
Tier III без валидного пруфа получает XP и урон как Tier II.

- Если подтверждение уже известно, передать его в `proof_text` при
  `complete_task`. Не выдумывать детали и не дополнять текст ради длины.
- Если детали появились после выполнения сегодня и `add_proof` доступен,
  вызвать его: задача останется выполненной, а награда будет пересчитана.
  Если инструмента нет, не имитировать это через отмену и повторный зачёт.
- Пруф приватен по умолчанию. `share_proof: true` в `complete_task` или
  `share: true` в `add_proof` передавать только по явной просьбе пользователя.

## Задачи и расписания

Для кастомной задачи использовать:

- `oneshot` — одно выполнение;
- `weekly_n` — повторяемая задача, `schedule_count` от 1 до 7.

`daily` предназначен для каталожных пресетов и старых клиентов. Новая
кастомная `daily` нормализуется в `weekly_n`, по умолчанию 7 раз за неделю.
Повторяемость не следует угадывать по одному эпизоду: Levelzzz сам предлагает
закрепление после трёх одноимённых разовых выполнений за 14 дней с разбросом
не менее семи дней.

Ориентир по тирам:

- I — небольшая изолированная задача, примерно 5–15 минут;
- II — содержательный завершённый блок, примерно 30–60 минут;
- III — крупный многошаговый результат с ясными признаками 90+ минут.

При недостатке данных выбирать меньший tier. Количество сообщений, файлов или
коммитов само по себе не доказывает объём работы.

## Ограничения недельного плана

- Не более 21 строки контракта за неделю, включая уже израсходованные
  soft-removed строки.
- Бюджет объявленного объёма — 6300: стоимость I/II/III равна 50/150/400 ×
  число выполнений (`oneshot` = 1, `weekly_n` = N, `daily` = 7).
- Среди активных повторяемых задач допускается не более четырёх Tier II и двух
  Tier III. Разовые задачи не входят в эти tier-cap, но расходуют бюджет.
- Если остаток неизвестен, передать добавление серверу и честно пересказать
  результат; не обещать успех и не менять другие задачи ради лимита.

## XP, стрик и сверх плана

Базовый XP I/II/III: 10/25/50. Множитель стрика: ×1.0 для 0–2 дней, ×1.1 для
3–6, ×1.25 для 7–13, ×1.4 для 14–29 и ×1.5 для 30+ дней. Первое действие дня
даёт +10 XP; дневной потолок XP задач — 150. Первое выполнение аккаунта даёт
отдельные +250 XP вне дневного потолка.

После исчерпания `weekly_n` режим «сверх плана» даёт половину фактически
доступного XP, не наносит урон и не идёт в лигу или дневное комбо. Пока MCP не
экспонирует `over_plan`, не передавать этот параметр.

Награду для ответа не пересчитывать. После мутации показывать только
фактические XP, урон, уровень и стрик из результата MCP.

## Чтение и периодические проверки

- Задачи — `list_tasks`; прогресс и боссы — `get_progress`; профиль —
  `get_profile`; гильдия — `get_guild`; история — `get_history` с `limit` не
  более 50.
- Пересказывать данные коротко и конкретными цифрами, ничего не выдумывать.
- Периодическую проверку по умолчанию делать read-only. Если пользователь
  просит автоматические действия, сначала закрепить расписание, часовой пояс,
  источник контекста, разрешённые мутации, предел за запуск, дедупликацию и
  поведение при ошибке.
